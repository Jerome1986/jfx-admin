# 预约负责人及跟进接口契约

前端已按此契约接入；当前仓库不包含后端实现，需后端交付并联调后上线完整流程。

## 分配及改派

`PUT /api/appointment/{id}/assignee`

请求体：`{ "employeeId": 123 }`。员工标识必填且不可为空，必须对应在职员工。
首次分配和改派使用同一接口。改派必须选择不同于当前负责人的员工。
成功返回 `{ "code": 200, "message": "操作成功", "data": AppointmentDetail }`，详情结构与现有详情接口一致。
校验预约存在、员工存在且在职。仅更新预约负责人，不新增沟通记录、不改写历史跟进人员，不变更预约业务状态。

## 新增跟进

沿用 `POST /api/appointment/{id}/follow-up`，请求体包含 `content`、`nextFollowAt` 和必填的 `employeeId`。
内容去除首尾空格后不可为空；下次跟进时间为 ISO 日期时间字符串或 null。
成功返回统一响应，data 为新增的 `AppointmentFollowUp`。

后端必须在同一事务内校验预约已有负责人、请求 employeeId 等于预约当前 employeeId，再插入跟进记录。
与改派操作使用同一预约行锁或等效并发控制，确保校验与写入期间归属不变。
未分配时返回业务错误“请先分配负责人，再添加跟进”；归属冲突时返回“负责人已变更，请刷新预约后重新提交”。
失败响应使用现有统一错误结构（code 不等于 200，message 为可展示说明），不得写入跟进。
前端保留失败表单；归属冲突后需关闭弹窗、刷新预约并重新打开，不自动重试写请求。

## 联调验收

- 未分配预约：列表和详情显示分配操作，不能新增跟进；直接请求跟进接口也应被拒绝。
- 首次分配：选在职员工成功保存，列表及已打开详情刷新，随后允许跟进。
- 改派：当前负责人不可重复选择；历史记录归属不变，新跟进归属新负责人。
- 员工超过一页：加载完整列表；中途失败不展示部分结果，可重新加载。
- 保存失败：弹窗和输入保留；连续点击提交只产生一个写请求。
- 并发改派：用旧负责人提交跟进被拒绝，且不产生错误归属记录。
- 其他预留操作仍保持未接入提示，不伪造保存成功。
